## ADDED Requirements

### Requirement: Provider Keys Are Managed As Runtime Secrets
The system SHALL source Cap production provider credentials from AWS Secrets Manager and expose them to Kubernetes workloads only through runtime secrets.

#### Scenario: Provider keys are available to web runtime
- **WHEN** the Cap production deployment starts
- **THEN** `cap-web` SHALL receive `DEEPGRAM_API_KEY`, `GROQ_API_KEY`, `OPENAI_API_KEY`, and `REPLICATE_API_TOKEN` from Kubernetes Secret references
- **AND** secret values SHALL NOT appear in Git-tracked Helm values, Terraform code, logs, or OpenSpec artifacts

#### Scenario: Provider key rotation is traceable
- **WHEN** an operator needs to rotate provider credentials
- **THEN** the operator SHALL be able to rotate the AWS Secrets Manager secret `kubernetes/cap/provider-keys/production`
- **AND** the deployment SHALL document which Kubernetes Secret keys consume those rotated values

### Requirement: Self-Hosted Workflow Runtime Executes Cap Workflows
The system SHALL run Cap Workflow DevKit jobs in Kubernetes using a durable PostgreSQL-backed workflow world.

#### Scenario: Desktop segment finalization workflow starts
- **WHEN** a desktop recording completes segment upload
- **THEN** `queueDesktopSegmentsFinalization` SHALL enqueue and execute `finalizeDesktopRecordingWorkflow`
- **AND** the workflow SHALL call the media server `/video/mux-segments` endpoint

#### Scenario: Workflow state survives pod restart
- **WHEN** `cap-web` is restarted while workflow state exists
- **THEN** workflow state SHALL remain available in PostgreSQL
- **AND** queued or retryable workflow steps SHALL continue without relying on local pod filesystem state

#### Scenario: Workflow schema is initialized
- **WHEN** the Cap Helm release is deployed
- **THEN** the Workflow DevKit PostgreSQL setup SHALL run idempotently before workflow execution is considered ready
- **AND** repeated setup runs SHALL NOT corrupt existing workflow state

### Requirement: Media Processing Callback URL Uses Kubernetes Service Routing
The system SHALL configure media server callbacks to use an in-cluster web service URL that routes successfully to `cap-web`.

#### Scenario: Media server posts progress callback
- **WHEN** the media server sends a progress or completion webhook
- **THEN** it SHALL call the `cap-web` Kubernetes Service on an exposed service port
- **AND** the webhook SHALL be accepted by the web application when the shared media-server secret is valid

### Requirement: Scheduled Maintenance Runs In Kubernetes
The system SHALL replace required Vercel cron behavior with Kubernetes CronJobs managed by the Cap Helm chart.

#### Scenario: Stale desktop segment recovery runs periodically
- **WHEN** the Cap production chart is deployed
- **THEN** a Kubernetes CronJob SHALL call `/api/cron/finalize-stale-desktop-segments` every 15 minutes
- **AND** the request SHALL include `Authorization: Bearer $CRON_SECRET`

#### Scenario: Cron secret is required
- **WHEN** the CronJob runs
- **THEN** `CRON_SECRET` SHALL be read from a Kubernetes Secret
- **AND** the CronJob SHALL fail closed if the secret is missing or incorrect

#### Scenario: Developer storage cron is explicit
- **WHEN** developer storage billing cron is not intentionally enabled
- **THEN** the chart SHALL NOT schedule `/api/cron/developer-storage`
- **AND** enabling it SHALL require an explicit Helm value and documented schedule

### Requirement: Recording Processing Produces User-Visible Artifacts
The system SHALL process new recordings through muxing, transcription, and AI summary generation when provider keys and audio content are available.

#### Scenario: Desktop recording creates processed video assets
- **WHEN** a new desktop recording with valid segments completes upload
- **THEN** S3 SHALL contain `result.mp4`
- **AND** S3 SHALL contain expected preview or screenshot assets generated by the media workflow
- **AND** the video database source SHALL transition from `desktopSegments` to `desktopMP4`

#### Scenario: Recording with audio creates transcript
- **WHEN** a processed recording contains an audio track and `DEEPGRAM_API_KEY` is configured
- **THEN** Cap SHALL generate a transcript
- **AND** the share page SHALL show transcript availability after processing completes

#### Scenario: Recording with transcript creates AI summary
- **WHEN** a recording has a completed transcript and `GROQ_API_KEY` or `OPENAI_API_KEY` is configured
- **THEN** Cap SHALL generate AI summary metadata
- **AND** the share page SHALL show the AI summary after generation completes

### Requirement: Stuck Video Is Recovered After Runtime Verification
The system SHALL recover the known stuck video only after the production runtime is healthy.

#### Scenario: Recovery waits for successful fresh processing
- **WHEN** the workflow runtime, webhook URL, provider keys, and cron job changes are deployed
- **THEN** operators SHALL validate a fresh recording processes successfully before mutating video `dezxvbfyv1jy83c`

#### Scenario: Stuck video recovery is scoped
- **WHEN** operators recover video `dezxvbfyv1jy83c`
- **THEN** the recovery action SHALL target only that video id
- **AND** the action SHALL verify raw segments exist before retrying finalization

#### Scenario: Stuck video recovery is complete
- **WHEN** recovery for `dezxvbfyv1jy83c` completes
- **THEN** S3 SHALL contain the processed video artifact
- **AND** the database SHALL no longer show the video stuck in `desktopSegments` processing state
- **AND** transcript and summary generation SHALL be attempted when audio and provider prerequisites are available
